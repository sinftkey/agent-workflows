# 多人 / 多 Agent 协同工作流模板（通用）

> 适用于「多名开发者 + 多个 AI Agent」在同一仓库协作的**任意项目**。复制到新项目后按第 0 节适配；纯人类团队可以删除 Agent 相关章节。

## 0. 使用说明

常用占位符：`<默认分支>`、`<分支前缀>`、`<CI 名称>`、`<维护者>`、`<Review 人数>`、`<Agent 账号>`、`<任务系统>`。

适配步骤：

1. 替换所有占位符；
2. 确定分支模型（默认 trunk-based，见第 3 节）；
3. 决定是否启用 AI Agent：不启用就删除第 10、11 节；
4. 与 [git-workflow-template.md](git-workflow-template.md) 组合使用，分工如下；
5. 复制时相关的模板文件一起带走，并修正相对链接。

| 场景 | 使用 |
|------|------|
| 提交信息、命令级操作、本地检查、回退命令；PR 模板与基础 Review 清单 | [git-workflow-template.md](git-workflow-template.md) 第 4、5、7、8、10 节 |
| 角色权限、任务认领、多人 / 多 Agent 并行、冲突协调、发布节奏 | 本模板 |
| 文档如何与代码同步（通信设计） | [docs-communication.md](docs-communication.md) |

## 1. 核心原则

1. `<默认分支>` 永远可构建、可运行、可部署；
2. 所有变更走分支 + PR，任何人都不直接推送默认分支；
3. 一个分支 = 一个任务 = 一个明确 owner；
4. 机器检查（CI）前置，人类审批兜底；
5. 有 AI Agent 参与时：**Agent 可以开发，不能自审自合**；
6. 冲突不可怕，可怕的是单方面覆盖他人意图。

## 2. 角色与权限

| 角色 | 职责 | git 权限 |
|------|------|----------|
| 维护者 `<维护者>` | 规则制定、合并决策、发布 | 合并 PR、打 tag、管理分支保护 |
| 开发者 | 功能开发、修复、Review | 创建/推送分支、PR、approve |
| Reviewer | 审查 diff 与验证结果 | review、请求修改、approve |
| AI Agent `<Agent 账号>`（可选） | 有界任务、PR、按反馈修改 | 创建/推送分支、PR、评论；**无 approve** |

平台侧建议：

- `<默认分支>` 开启分支保护：禁止直接推送、CI 必须通过、至少 `<Review 人数>` 个 approve；
- `<Agent 账号>` 不授予默认分支直接推送权限；
- 合并与打 tag 仅授予维护者。

## 3. 分支模型与命名

### 3.1 分支模型

默认 trunk-based：

- 长期分支：`<默认分支>`；
- 短期功能分支：数天内合并，合并后删除；
- 需要固定版本：`release/vX.Y.Z`（只收 bugfix）；
- 线上紧急修复：`hotfix/<主题>`，从 `<默认分支>` 或最近 tag 创建。

### 3.2 分支命名（多人场景约定）

基础格式见 [git-workflow-template.md](git-workflow-template.md) 第 3.3 节；多人 / 多 Agent 场景在基础格式上统一带任务编号或 owner：

```text
<分支前缀>/<任务编号>-<type>-<主题>        # 例：<分支前缀>/42-feat-rate-limit
<分支前缀>/<owner>/<type>/<主题>          # 例：<分支前缀>/alice/feat/rate-limit
```

推荐带任务编号：PR、commit、issue 之间可互相追溯。**同一分支同一时间只允许一个写入者**。

## 4. 任务认领与分支所有权

git 没有「锁」，多 Agent 并行靠纪律：

1. 任务在 `<任务系统>` 登记，**owner 必填**（人类或某个 Agent）；
2. 分支与任务一一对应，分支名体现任务编号或 owner；
3. 开工前检查：目标文件近期是否有人改过（`git log -- <path>`、查看进行中的 PR 列表），避免撞车；
4. 需要多人改同一批文件时：拆子任务串行合并，或明确先后顺序，**不并行修改同一文件**；
5. 发现分支上有他人新提交：先沟通，再决定继续、合流或换分支，不直接覆盖。

## 5. 日常协作循环

```text
认领任务 → 登记分支 → 同步 <默认分支> → 开发提交 → 本地验证
→ rebase 最新 → push → 创建 PR → CI → Review → 修改反馈
→ 人类 approve → 合并 → 删除分支 → 全员同步
```

### 5.1 同步与开发

```shell
git fetch origin
git switch -c <分支前缀>/42-feat-rate-limit origin/<默认分支>
# 小步提交，每个提交独立可验证
```

### 5.2 推送前

```shell
git fetch origin
git rebase origin/<默认分支>

# 项目规定的完整检查（格式化 / 静态检查 / 测试 / 构建，见 git-workflow-template.md 第 5 节）

git push -u origin <分支前缀>/42-feat-rate-limit
```

### 5.3 PR 与 Review

- PR 描述按第 6 节模板填写；
- 机械问题可由另一个 Agent 先互审，**最终 approve 必须来自人类**；
- 收到反馈后在分支上**新增提交**回应，不 `--amend` 已推送提交、不 force push；
- 逐条回复意见的处置结果。

## 6. PR 模板

PR 模板正文（关联任务、改动概述、验证结果、影响范围、文档同步、安全声明）由 [git-workflow-template.md](git-workflow-template.md) 第 7 节统一维护，本模板不重复。多人场景的要求：

- 「文档同步」字段必须给出明确结论（列出已更新文档路径，或声明无需更新并说明理由）；
- PR 的 Review 与修改流程见第 5.3 节与 7.2 节。

## 7. Review 规则

### 7.1 基础检查清单

通用基础清单（逻辑、测试、密钥、风格、文档同步、无关改动、错误处理等）由 [git-workflow-template.md](git-workflow-template.md) 第 8 节统一维护，本模板不重复。

### 7.2 多人 / 多 Agent 补充

补充检查：

- [ ] 改动文件与分支声明一致，未覆盖他人正在修改的模块
- [ ] 作者逐条回复了 review 意见
- [ ] 合并前有**人类**做了最终 review

规则：

- Agent 互审可以快，但默认分支合并前必须有**人类 approve**；
- Review 意见带行号与可执行建议；
- Reviewer 与作者不在同一分支直接互改：作者负责改，Reviewer 负责看。

## 8. 冲突与协调

- 预防：小步提交、频繁同步 `<默认分支>`、文件级避让；
- 处理：先理解对方提交意图 → 保留双方合理部分 → 涉及取舍先沟通 → 重新完整验证；
- 同一区域频繁冲突时，停下调整任务拆分或模块边界，不硬顶；
- 禁止命令（`git reset --hard`、`git checkout -- .`、`git clean -fdx`、`git push --force` 等）见 [git-workflow-template.md](git-workflow-template.md) 第 10 节，除非用户 / 维护者明确要求不得使用。

## 9. 合并与发布

- 默认 **Squash and merge**，保持 `<默认分支>` 历史线性；
- 需要保留协作分支历史时由维护者决定普通 merge；
- 合并后立即删除分支，定期 `git fetch --prune`；
- 发布 = 打 tag `vX.Y.Z` + release notes；破坏性变更升级 major；
- hotfix：从 `<默认分支>`/tag 创建 → 修复验证 → 人类快速 approve → 合并打新 tag → cherry-pick 回功能分支。

## 10. Agent 行为规范（无 Agent 时删除本节）

1. 开工前必读：`AGENTS.md` / `CONTRIBUTING.md` 及任务相关文档；
2. 任务有界：只改任务范围内内容，不顺手重构无关代码；
3. 不覆盖他人：push 前 `fetch` + `rebase`；发现对方新提交先沟通；
4. 诚实报告：验证失败、不确定、超出权限时如实说明，不声称「已通过」；
5. PR 必须按模板填写，附真实验证证据；
6. 不请求自己未获授权的权限（approve、合并、打 tag）；
7. 对 review 意见逐条回应，改动后说明结论。

## 11. 多 Agent 并行协调细则

- 一个任务同时只分配给一个 Agent；一个 Agent 同一时间的活跃分支数不超过团队约定上限；
- 可选：建立「模块 ↔ owner」表，公共模块改动前先通知 owner；
- 公共接口 / 配置 / 数据结构变更：**先更新文档，再改代码**，避免其他 Agent 基于旧文档开发；
- 互审对象由维护者分配，Agent 不自行挑选 reviewer；
- 两个 Agent 的 PR 出现重叠文件时，由维护者决定合并顺序，后合并的一方负责解决冲突。

## 12. 检查清单

### push 前

- [ ] 分支名符合约定，只有我在写入
- [ ] 已 fetch 并基于最新 `<默认分支>`
- [ ] 完整检查通过
- [ ] 提交只含本任务改动
- [ ] 无密钥、大文件、无关文件

### 合并前

- [ ] PR 描述完整（任务、概述、验证、影响、文档同步、安全声明）
- [ ] CI 通过
- [ ] 人类 approve（至少 `<Review 人数>` 个）
- [ ] 文档与代码一致
- [ ] 合并策略符合约定

## 13. 与 git-workflow-template.md 的组合

分工见第 0 节表格：提交与命令级操作、PR 模板、基础 Review 清单由 git-workflow-template.md 维护；本模板只负责协作层规则。

两个模板一起复制到新项目，保留相对链接、替换占位符即可；只复制其中一份时，把指向另一份的引用链接一并删除或修正。
