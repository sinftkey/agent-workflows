# 多人 / 多 Agent 协同工作流模板（通用）

> 适用于「多名开发者 + 多个 AI Agent」在同一仓库协作的**任意项目**。复制到新项目后按第 0 节适配；纯人类团队可以删除 Agent 相关章节。

## 0. 使用说明

常用占位符：`<默认分支>`、`<Agent 工具名/角色/身份>`、`<CI 名称>`、`<维护者>`、`<Review 人数>`、`<Agent 账号>`、`<任务系统>`。

适配步骤：

1. 替换所有占位符；
2. 确定分支模型（默认 trunk-based，见第 4 节）；
3. 决定是否启用 AI Agent：不启用就删除第 11、12 节（角色权限矩阵中 AI Agent 行一并删除或忽略）；
4. 与 [git-workflow-template.md](git-workflow-template.md) 配套使用，分工如下；
5. 复制时相关的模板文件一起带走，并修正相对链接。

| 场景 | 使用 |
|------|------|
| 提交信息、命令级操作、本地检查、回退命令；PR 模板与基础 Review 清单 | [git-workflow-template.md](git-workflow-template.md) 第 4、5、7、8、10 节 |
| 角色权限矩阵、标准流程编排、任务认领、多人 / 多 Agent 并行、冲突协调、发布节奏 | 本模板 |
| 文档如何与代码同步（通信设计） | [docs-communication.md](docs-communication.md) |

## 1. 核心原则

1. `<默认分支>` 永远可构建、可运行、可部署；
2. 所有变更走分支 + PR，任何人都不直接推送默认分支；
3. 一个分支 = 一个任务 = 一个明确 owner；
4. 机器检查（CI）前置，人类审批兜底；
5. 有 AI Agent 参与时：Agent 按角色行事，**不得自审自批**，合并与发布必须由维护者执行；
6. 角色权限分离：开发写代码、审核提意见、测试产用例，**正式测试用例的唯一来源是测试角色**；
7. 冲突不可怕，可怕的是单方面覆盖他人意图。

## 2. 角色与权限

### 2.1 角色职责

| 角色 | 职责 | git 权限 |
|------|------|----------|
| 维护者 `<维护者>` | 规则制定、合并决策、发布 | 合并 PR、打 tag、管理分支保护 |
| 开发 | 功能开发、缺陷修复、按 review 反馈修改 | 创建/推送分支、发起 PR |
| 审核（Reviewer） | 审查 diff 与验证结果，提出修改意见 | review、request changes、approve；**无提交权、无合并权** |
| 测试（Tester） | 编写正式测试用例、运行测试、报告验证结果 | 创建/推送分支、发起**仅含测试文件**的 PR |
| AI Agent `<Agent 账号>`（可选） | 以某个角色（开发 / 审核 / 测试）身份参与，按该角色权限行事 | 同所扮演的角色 |

### 2.2 权限矩阵（能做什么 / 不能做什么）

| 操作 | 开发 | 审核 | 测试 |
|------|------|------|------|
| 修改生产代码 / 配置 / 文档 | ✅ | ❌ 绝不修改 | ❌ 绝不修改 |
| 编写测试文件 | ⚠️ 仅本地一次性自验：**写 → 测 → 删**，不提交、不采信 | ⚠️ 仅本地临时验证 review 意见：修改内容与验证结果必须呈现在意见中，**绝不提交 git** | ✅ 正式测试用例的唯一来源 |
| 提交 / 发起 PR | ✅（生产代码 + 文档） | ❌ 永不提交 | ✅（仅测试文件） |
| approve | ❌ | ✅（合并仍由维护者执行） | ❌ |
| 合并 / 打 tag / 发布 | ❌ | ❌ | ❌ |

要点：

- 开发的自验测试、审核的验证测试都**不采信、不入库**，PR 的验证证据只引用测试角色的用例与结果；
- 超出角色权限的操作视为越权：Agent 不得请求、不得执行，人类角色也应避免代劳；
- 任务开始前确认参与角色（分支前缀或任务登记中体现），后续所有操作以该角色为准。

平台侧建议：

- `<默认分支>` 开启分支保护：禁止直接推送、CI 必须通过、至少 `<Review 人数>` 个 approve；
- `<Agent 账号>` 不授予默认分支直接推送权限；
- 合并与打 tag 仅授予维护者。

## 3. 标准流程编排

角色按标准软件开发流程协作：**需求 → 开发 → 测试 → 审核 → 发布**。支持两种节奏：

### 3.1 测试先行（TDD）

```text
需求（含验收标准） → 测试角色先写验收用例并提交 → 开发实现直至测试通过
→ 测试角色复跑确认 → 审核 → 维护者 approve + 合并 → 发布
```

- 适用：接口、算法、缺陷修复等验收标准可先写为测试的任务；
- 落地方式：测试角色的用例 PR 先行合并，开发在其上实现；或同一分支由测试先提交用例、开发后续提交实现。

### 3.2 开发先行

```text
需求 → 开发实现（本地一次性自验，即写即测即删）→ 测试角色编写正式用例、提交测试 PR 并报告结果
→ 审核（只采信测试角色的验证结果）→ 维护者 approve + 合并 → 发布
```

- 适用：探索性、边界不清晰、需要先跑通再定验收标准的任务；
- 开发的自验测试与自验结果**不提交、不采信**，不作为 PR 验证证据；PR 验证结论只引用测试角色的用例与结果。

### 3.3 各环节责任

| 环节 | 责任角色 | 产出 / 动作 |
|------|----------|-------------|
| 需求 / 任务 | 维护者或任务发起人 | 任务登记、owner、验收标准 |
| 开发 | 开发 | 生产代码 + 文档，PR 附验证证据 |
| 测试 | 测试 | 正式用例（仅测试文件的 PR）+ 验证结果报告 |
| 审核 | 审核 | review 意见、request changes / approve；绝不改代码、绝不提交 |
| 合并 / 发布 | 维护者 | approve 后合并、打 tag、release notes |

## 4. 分支模型与命名

### 4.1 分支模型

默认 trunk-based；分支模型（长期分支、功能分支、`release/`、`hotfix/`）见 [git-workflow-template.md](git-workflow-template.md) 第 3.1 节。

### 4.2 分支命名（多人场景约定）

基础格式见 [git-workflow-template.md](git-workflow-template.md) 第 3.3 节；多人 / 多 Agent 场景在基础格式上统一带任务编号或 owner：

```text
<Agent 工具名/角色/身份>/<任务编号>-<type>-<主题>        # 例：<Agent 工具名>/42-feat-rate-limit
<Agent 工具名/角色/身份>/<owner>/<type>/<主题>          # 例：<Agent 工具名>/alice/feat/rate-limit
```

推荐带任务编号：PR、commit、issue 之间可互相追溯。**同一分支同一时间只允许一个写入者**。

## 5. 任务认领与分支所有权

git 没有「锁」，多 Agent 并行靠纪律：

1. 任务在 `<任务系统>` 登记，**owner 必填**（人类或某个 Agent）；
2. 分支与任务一一对应，分支名体现任务编号或 owner；
3. 开工前检查：目标文件近期是否有人改过（`git log -- <path>`、查看进行中的 PR 列表），避免撞车；
4. 需要多人改同一批文件时：拆子任务串行合并，或明确先后顺序，**不并行修改同一文件**；
5. 发现分支上有他人新提交：先沟通，再决定继续、合流或换分支，不直接覆盖。

## 6. 日常协作循环

```text
认领任务 → 登记分支 → 同步 <默认分支> → 开发提交 → 本地验证
→ rebase 最新 → push → 创建 PR → CI → Review → 修改反馈
→ 审核 approve → 维护者合并 → 删除分支 → 全员同步
```

> 节奏按第 3 节标准流程编排执行：测试角色的用例 PR、开发的实现 PR 都走本循环，但分支内容受第 2.2 节权限矩阵约束（测试分支仅测试文件，审核永不提交）。

### 6.1 同步与开发

```shell
git fetch origin
git switch -c <Agent 工具名/角色/身份>/42-feat-rate-limit origin/<默认分支>
# 小步提交，每个提交独立可验证
```

### 6.2 推送前

```shell
git fetch origin
git rebase origin/<默认分支>

# 项目规定的完整检查（格式化 / 静态检查 / 测试 / 构建，见 git-workflow-template.md 第 5 节）

git push -u origin <Agent 工具名/角色/身份>/42-feat-rate-limit
```

### 6.3 PR 与 Review

- PR 描述按第 7 节模板填写；
- 机械问题可由另一个 Agent 先互审，审核 Agent 可 approve，**合并必须由维护者执行**；
- 收到反馈后在分支上**新增提交**回应，不 `--amend` 已推送提交、不 force push；
- 逐条回复意见的处置结果。

## 7. PR 模板

PR 模板正文（关联任务、改动概述、验证结果、影响范围、文档同步、安全声明）由 [git-workflow-template.md](git-workflow-template.md) 第 7 节统一维护，本模板不重复。多人场景的要求：

- 「文档同步」字段必须给出明确结论（列出已更新文档路径，或声明无需更新并说明理由）；
- 测试角色的 PR：改动范围**只允许测试文件**，验证结果字段给出实际运行输出；
- 开发的 PR：验证结果**只引用测试角色的用例与结果**，不引用开发自验测试；
- PR 的 Review 与修改流程见第 6.3 节与 8.2 节。

## 8. Review 规则

### 8.1 基础检查清单

通用基础清单（逻辑、测试、密钥、风格、文档同步、无关改动、错误处理等）由 [git-workflow-template.md](git-workflow-template.md) 第 8 节统一维护，本模板不重复。

### 8.2 多人 / 多 Agent 补充

补充检查：

- [ ] 改动文件与分支声明一致，未覆盖他人正在修改的模块
- [ ] 作者逐条回复了 review 意见
- [ ] 合并前有**人类**做了最终 review
- [ ] 开发的 PR 中无自验测试残留；测试的 PR 中无生产代码改动
- [ ] 验证结果可复现（引用的用例与命令明确）

规则：

- Agent 互审可以快；审核角色（人类或 Agent）可 approve，但**合并必须由维护者执行**；
- 审核**只提意见、不改作者分支**：确需本地验证时，临时改动测试并运行，修改内容与验证结果必须完整呈现在 review 意见中，**绝不提交 git**；
- Review 意见带行号与可执行建议；
- Reviewer 与作者不在同一分支直接互改：作者负责改，Reviewer 负责看。

## 9. 冲突与协调

- 预防：小步提交、频繁同步 `<默认分支>`、文件级避让；
- 处理：先理解对方提交意图 → 保留双方合理部分 → 涉及取舍先沟通 → 重新完整验证；
- 同一区域频繁冲突时，停下调整任务拆分或模块边界，不硬顶；
- 禁止命令（`git reset --hard`、`git checkout -- .`、`git clean -fdx`、`git push --force` 等）见 [git-workflow-template.md](git-workflow-template.md) 第 10 节，除非用户 / 维护者明确要求不得使用。

## 10. 合并与发布

合并策略（默认 squash、历史线性、合并后删分支等）由 [git-workflow-template.md](git-workflow-template.md) 第 9 节统一维护，本模板不重复。本节只补充发布节奏：

- 发布 = 打 tag `vX.Y.Z` + release notes；破坏性变更升级 major；
- hotfix：从 `<默认分支>`/tag 创建 → 修复验证 → 人类快速 approve → 合并打新 tag → cherry-pick 回功能分支。

## 11. Agent 行为规范（无 Agent 时删除本节）

1. 开工前必读：`AGENTS.md` / `CONTRIBUTING.md` 及任务相关文档，并**确认自身角色**（见第 2 节）；
2. 任务有界：只改任务范围内内容，不顺手重构无关代码；操作不超出自身角色权限（见第 2.2 节矩阵）；
3. 开发角色的自验测试**即写即测即删**：不提交、不作为验收依据；审核角色绝不提交 git；测试角色只提交测试文件；
4. 不覆盖他人：push 前 `fetch` + `rebase`；发现对方新提交先沟通；
5. 诚实报告：验证失败、不确定、超出权限时如实说明，不声称「已通过」；
6. PR 必须按模板填写，附真实验证证据（开发引用测试角色的结果，不引用自验）；
7. 不请求自己未获授权的权限（合并、打 tag、越出自身角色的操作）；
8. 对 review 意见逐条回应，改动后说明结论。

## 12. 多 Agent 并行协调细则

- 一个任务同时只分配给一个 Agent；一个 Agent 同一时间的活跃分支数不超过团队约定上限；
- 可选：建立「模块 ↔ owner」表，公共模块改动前先通知 owner；
- 公共接口 / 配置 / 数据结构变更：**先更新文档，再改代码**，避免其他 Agent 基于旧文档开发；
- 互审对象由维护者分配，Agent 不自行挑选 reviewer；
- 两个 Agent 的 PR 出现重叠文件时，由维护者决定合并顺序，后合并的一方负责解决冲突；
- 开发与测试并行时：测试先用例、开发后实现（3.1），或开发先行、测试随后补用例（3.2），同一分支的写入顺序按第 3 节约定，避免互相覆盖。

## 13. 检查清单

### push 前

- [ ] 分支名符合约定，只有我在写入
- [ ] 已 fetch 并基于最新 `<默认分支>`
- [ ] 完整检查通过
- [ ] 提交只含本任务改动
- [ ] 提交内容符合自身角色（开发：生产代码 + 文档；测试：仅测试文件；审核：不提交）
- [ ] 无密钥、大文件、无关文件，无自验测试残留

### 合并前

- [ ] PR 描述完整（任务、概述、验证、影响、文档同步、安全声明、请 reviewer 重点看）
- [ ] `<CI 名称>` 通过
- [ ] 审核 approve（至少 `<Review 人数>` 个，可由审核 Agent 给出）
- [ ] 验证结果引用测试角色的用例与结果
- [ ] 文档与代码一致
- [ ] 合并策略符合约定
